# 开发与排错

## 开发环境

在插件目录执行：

```bash
python -m pip install -r requirements.txt
python -m pip install pytest ruff

python -m pytest -q
python -m ruff check .
python -m ruff format --check .
python -m compileall -q main.py motion_vision
```

如果要在本地运行 AstrBot，请按 AstrBot 的开发文档准备宿主环境；插件本身不把宿主的配置、凭据或临时文件提交到仓库。

## 处理边界

媒体处理大致经过以下阶段：

1. 从消息链、原始平台 payload、附件和引用中收集候选；
2. 识别动图、视频、B 站内容和卡片；
3. 对下载、响应体、文本和重定向做大小与来源限制；
4. 为动图和视频分别计算采样计划；
5. 在本轮共享图片张数和体积预算；
6. 提取画面、音轨、字幕和专栏等证据；
7. 通过唯一注入边界交给 `ProviderRequest`；
8. 登记可回看的源文件，并在生命周期结束后清理。

采样算法是纯函数，尽量不把 IO、平台对象和模型请求混在一起，因此可以直接用单测验证边界情况。

## 设计原则

### 失败可降级

画面、声音、字幕、卡片和整片模型互相独立。视频模型失败时仍尝试关键帧；字幕失败不应阻断画面；单个坏附件不应让整条对话崩溃。

### 预算先行

每个媒体有自己的安全上限，多媒体还共享整轮抽帧图片数量和总体积预算。混合消息优先满足视频目标，剩余额度在动图之间均分；预算足够时，每张动图先预留最多两帧。同类媒体按需求均分，只有动图的消息不受视频优先规则影响。

体积按最终均匀取样后的实际帧大小核算，不能假设每张图片大小相同。张数与体积一并规划后，再从原始时间轴抽稀一次；原始缓存不受本轮裁剪影响。帧被预算全部裁掉时，也要移除对应的原始附件，避免它绕过预算再次进入请求。

### 并发受控

媒体处理、ffmpeg、STT、B 站接口、下载和必剪上传使用闸门或串行策略。外部接口遇到 429 只做有限退避，不能通过无限重试制造请求风暴。超时任务必须等待尾部退出，避免下一轮与旧任务重叠。

### 外部资料不具备指令权限

字幕、专栏正文、卡片字段和原生模型报告都以资料形式注入。实现中不应执行其中的命令、提示词或 URL；新增来源时也必须保持这个边界。

### 凭据隔离

B 站 Cookie 只用于 B 站相关请求；必剪音频上传使用独立客户端，不应携带 B 站凭据。日志、状态和用户可见错误不能泄露密钥。

## 排错

注入日志的“外部资料条数”不代表已读取正文。0.8.0 起会分别统计正文、仅元数据、失败和正文字符数，每篇资料也有 `状态=body/metadata/failed` 日志；标题、密钥和正文不写入这类日志。“媒体资料”表示视频元数据或字幕上下文，“转写”表示单独的语音转写/模型报告。

专栏应能看到 `状态=body` 与非零正文字符数；若只有 `metadata`，检查页面访问、登录态及是否遇到 B 站验证。QQ 卡片通过 `message_obj.raw_message`、标准组件或有界 `get_msg` 回查提取；自动注入和分页阅读都使用用户内容，避免改写系统提示词。

### 视频没有画面

1. 执行 `/motionvision status`；
2. 确认 ffmpeg 能在宿主系统执行，或在高级配置填写正确路径；
3. 检查视频大小、处理超时和单条消息视频数量限制；
4. 先测试本地小文件，再测试远程附件或 B 站下载；
5. 如果只有整片模型失败，确认本地关键帧是否仍能生成。

### 动图只看到一帧

确认文件确实是动态 WebP/APNG/GIF，并检查源文件是否只有一帧。图片数量受限时可选择小宫格；若接口严格只接受一图，还需把单轮图片上限设为 1，这只会保留一页而非任意多帧。自动模式不会为了凑数重复源帧。

### B 站内容不完整

B 站下载、字幕和专栏是不同证据层。先查看状态和日志，再分别确认：

- 链接是否包含正确的分 P；
- yt-dlp 是否能访问该视频；
- 是否需要 Cookie 或扫码登录；
- 官方字幕是否存在；
- 是否开启了必剪回退；
- 当前接口是否正在限流。

即使视频文件拿不到，标题、简介、元数据和字幕仍可能可用。

### 整片视频模型没有请求

确认：

- 模式不是关闭；
- API Key、地址和模型名正确；
- 选定协议与服务商接口匹配；
- 视频没有超过上传限制；
- 按需模式下模型确实调用了 `analyze_motion_video`；
- 回看已开启，因为按编号的整片工具依赖媒体档案。

### 模型没有回看

回看依赖当前服务商允许工具调用、模型具备图片输入能力，以及插件开启回看。回看源文件过期后，如果原始地址失效，工具会如实返回不可恢复。

### 出现 429

不要立即并行重试。插件本身只做有限退避并优先使用缓存；持续限流时让本轮降级，稍后再试。排查时可以：

- 关闭自动整片模式，改成按需；
- 降低同一消息中的媒体数量；
- 暂时关闭必剪字幕回退；
- 等待上游窗口恢复；
- 检查是否有宿主或其他插件同时请求同一服务。

## 修改代码前的检查

- 新增配置项时同步更新配置读取、默认值、限幅和文档；
- 新增外部请求时设置超时、响应大小限制、重定向/域名边界和有限重试；
- 新增媒体来源时加入去重、循环引用保护和共享回查；
- 新增证据时明确标记来源，不能把外部文字变成系统指令；
- 任何影响采样的改动都补充纯函数单测；
- 保持 `main.py` 只做编排，复杂逻辑放入可测试模块；
- 不把密钥、Cookie、临时媒体或本地缓存提交到仓库。

## 宿主与文件生命周期

宿主在请求钩子之前可能已把动图转为宫格。`host_images.py` 根据宿主生成的原图路径和视觉序号精确关联，编号顺序为 extra 图片在前、image_urls 在后；不按文件名、图像外观或相邻位置猜测。未知标记格式保守保留，不安装全局 monkeypatch。这个适配在宿主标记格式变化时需要回归验证。

源帧、宫格和原音缓存按完整 SHA-256 与产物配置隔离。同内容任务按键串行生成。预算只裁剪返回副本，不能污染缓存。文件租约覆盖请求、回看和后台编码；取消协程不会提前释放仍在工作的线程文件或解码并发名额。主请求结束由响应钩子释放，失败请求还有事件回收兜底。

Pillow 的时间限制是在帧间检查的协作式限制，不是能杀掉任意单帧解码的硬超时；因此源大小、单帧像素、累计像素和源帧数限制必须同时保留。
