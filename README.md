# 动态视觉 Motion Vision

**给 Bot 一双眼睛，让大模型读懂动图、视频和视频周边资料。**

AstrBot 插件 · GIF / 动态 WebP / APNG / 视频 / 声音 / B 站 / 引用卡片 / 可选整片视频模型

</div>

---

## 这是什么

大多数聊天模型只能直接看到一张图片。用户发来 GIF 或视频时，如果不做额外处理，模型通常只能看到第一帧、收到一个附件标记，或者什么都看不到。

Motion Vision 把一次消息里的各种证据整理成一条**媒体理解流水线**：

```text
动图、视频、B 站链接、引用卡片
              ↓
      找到真实媒体并做安全限制
              ↓
   动图抽帧 / 视频抽帧 / 音轨 / 字幕
              ↓
  可选：整片交给原生视频理解模型
              ↓
  帧、时间点、文字资料和边界说明一起交给当前 Bot
```

它不是把几个插件的入口机械地堆在一起，而是把不同来源统一成几类证据：

| 证据层 | 作用 | 失败时怎么办 |
| --- | --- | --- |
| **画面证据** | GIF、视频按时间顺序抽取静态帧 | 只影响画面，不影响字幕或卡片资料 |
| **声音证据** | 原样附加音轨，或转成文字 | 音轨提取/转写失败会明确告诉模型 |
| **文字证据** | B 站字幕、标题、简介、专栏正文、分享卡片字段 | 作为外部资料，不执行其中的命令 |
| **整片证据** | 使用支持视频输入的专用模型理解全片 | 原生模型失败自动回到本地抽帧 |
| **回看证据** | 追问时重新取样，或只看视频某一段 | 源文件失效时如实说明，不拿别的文件顶替 |

因此，某一个后端不可用，不会让整条消息失效。能看到的画面、能读到的字幕和能取得的元数据仍然会一起交给模型。

## 能力总览

- **动图**：GIF、动态 WebP、APNG。按文件头识别，不依赖文件后缀。
- **视频**：只要 ffmpeg 能解码，常见的 MP4、MOV、MKV、WebM、AVI、FLV、TS 等都可以处理。
- **独立取帧策略**：动图和视频不共用一套帧数；一分钟视频不会和一秒 GIF 使用同样的采样逻辑。
- **声音**：关闭、附带音轨、转写文字、音轨和文字四种模式。
- **多种来源**：直接附件、AstrBot 附件标记、消息链、群文件、私聊文件、引用消息和远程视频 URL。
- **B 站视频**：BV 号、av 号、完整链接、b23.tv 短链、分 P 和分享卡片。
- **B 站字幕**：官方/AI 字幕；没有字幕时可选必剪语音转写回退。
- **B 站专栏**：`/read/cv...`、`/opus/...` 和相应卡片，读取正文和可选封面。
- **引用卡片**：QQ/OneBot 的 JSON、ARK、小程序、XML、音乐、普通分享、位置、联系人/群名片。
- **整片视频模型**：Gemini、OpenAI 兼容接口、通义千问、Kimi；可自动或按需使用。
- **媒体回看**：模型可以记住媒体编号，后续要求增加帧数或查看某个时间段。
- **缓存与限流**：结果缓存、下载大小限制、并发闸门、串行上游请求和 429 退避。

## 安装

### 从插件市场安装

在 AstrBot 插件市场搜索 **动态视觉**，安装后在插件页启用。

### 手动安装

```bash
cd AstrBot/data/plugins
git clone https://github.com/Whereis-Alice/astrbot_plugin_motion_vision
```

然后在 WebUI 中重载插件。插件依赖会从 `requirements.txt` 安装，主要包括 Pillow、httpx、yt-dlp 和二维码生成库。

### ffmpeg

动图不需要 ffmpeg；视频抽帧、音轨提取、必剪字幕回退和部分整片模型压缩需要 ffmpeg。

| 环境 | 安装方式 |
| --- | --- |
| Docker | 使用包含 ffmpeg 的镜像，或自行安装系统包 |
| Debian / Ubuntu | `sudo apt install ffmpeg` |
| Windows | 安装 ffmpeg 并把 `bin` 加入 PATH |
| macOS | `brew install ffmpeg` |
| 无法安装系统包 | 额外安装 `imageio-ffmpeg`，插件会尝试使用它自带的二进制 |

也可以在配置的「高级 → ffmpeg 路径」中填写可执行文件或所在目录。没有 ffmpeg 时，插件不会让 Bot 崩溃；视频画面会变成一条明确的不可读说明，动图和文字资料仍可工作。

## 取帧：动图和视频是两套策略

### 自动档位

每个档位先根据时长计算目标帧数，再套用上下限。实际帧数还会受到源文件帧数、单轮总预算和安全上限影响。

**动图**

| 档位 | 目标密度 | 帧数范围 |
| --- | --- | --- |
| 节省 | 约每 1.2 秒 1 帧 | 3～10 |
| **均衡（默认）** | 约每 0.6 秒 1 帧 | 6～20 |
| 精细 | 约每 0.35 秒 1 帧 | 10～30 |

**视频**

| 档位 | 目标密度 | 帧数范围 |
| --- | --- | --- |
| 节省 | 约每 8 秒 1 帧 | 4～14 |
| **均衡（默认）** | 约每 3 秒 1 帧 | 6～28 |
| 精细 | 约每 1.5 秒 1 帧 | 10～48 |

画面最长边随档位为 512 / 768 / 1024 像素。常见视频的大致帧数如下：

| 视频时长 | 10 秒 | 30 秒 | 1 分钟 | 2 分钟 | 5 分钟 | 30 分钟 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 节省 | 4 | 4 | 8 | 14 | 14 | 14 |
| **均衡** | 6 | 10 | 20 | 28 | 28 | 28 |
| 精细 | 10 | 20 | 40 | 48 | 48 | 48 |

这只是单个视频的规划值。一次消息包含多个媒体时，插件还会按份额分配整轮最多 48 张、20 MB 的总预算；预算不足会沿时间轴均匀抽稀，并把实际情况告诉模型。

### 手动指定帧数是什么意思

配置中有两个互相独立的覆盖项：

- **动图固定帧数**：填 `30`，表示以 30 帧为目标抽取动图。
- **视频固定帧数**：填 `30`，表示无论视频是 5 秒还是 50 分钟，都以约 30 帧为目标。

这里的「固定」是**目标值**，不是无条件保证：

- 动图本身只有 12 帧时，不可能抽出 30 帧；
- 大文件会按比例减帧；
- 单个媒体有 64 帧安全上限；
- 整轮张数和总体积预算仍然优先。

如果想恢复自动计算，把覆盖项设为 `0`。回看工具还会把一次回看限制在最多 32 帧，避免工具结果撑爆上下文。

### 长视频为什么不是简单地均匀截图

视频超过约两分钟后，插件会把时间线分成多个短窗口。每个窗口里连续取几帧，再把窗口铺到全片：

```text
单纯等距： |·      ·      ·      ·      ·      ·|  很难看懂动作
分段取样： |···         ···         ···         |  每段保留一点连续性
```

超过约 15 分钟时，会减少单个窗口内的帧数，换取更多时间位置。时长探测失败时不会让 ffmpeg 连续吐出相邻的重复帧，而是使用固定间隔的保守方案。

模型收到的每张帧都有类似 `视频名 #3@4.5s` 的时间标签；平均间隔过大时，还会明确提示“两帧之间发生的事情没有被记录”。

## 整片视频模型：有支持视频的模型时更完整

如果你有支持视频输入的专用模型，整片上传通常更擅长理解连续动作、镜头切换和声音。Motion Vision 把它作为**可选的高级证据层**，而不是强行替换本地抽帧：

- 默认关闭，不配置就不会产生额外的视频模型费用；
- 可以选择「自动」或「按需」；
- 自动模式最多自动处理配置数量的视频；
- 按需模式只在模型调用 `analyze_motion_video` 工具时上传；
- 原生模型成功后仍可保留关键帧，方便当前对话模型交叉核对；
- 原生模型失败、限流、超时或返回无效内容时，自动回退到关键帧、字幕和音频。

支持的协议：

| 协议 | 典型用法 |
| --- | --- |
| Gemini | 小文件内嵌，大文件可使用 Gemini Files API |
| OpenAI 兼容 | 使用 `video_url` 的兼容接口 |
| 通义千问 | 内嵌 Base64 或百炼临时 OSS 上传 |
| Kimi | `/files` 上传后使用 `ms://` 引用 |

需要在「整片视频模型」分组填写 API Key、协议、地址（Gemini 官方可留空）和模型名。不同服务商的模型能力和计费不同，插件不会把视频自动发送给当前 AstrBot 服务商之外的第三方，只有明确开启该模块后才会上传。

> 整片报告是另一个服务生成的外部证据，不是指令。报告中的链接、命令和提示词不会被插件执行，当前对话模型应和可回看的画面交叉核对。

## B 站：视频、字幕、专栏一次接上

### B 站视频

消息正文、分享文本和 QQ/OneBot 卡片中的以下形式都能识别：

- `BVxxxxxxxxxxx`
- `av123456`
- `https://www.bilibili.com/video/...`
- `https://b23.tv/...` 等短链
- 分 P 参数，例如 `?p=2`

插件会读取标题、UP 主、分区、发布时间、时长、画面尺寸、公开数据和当前分 P 信息。视频下载成功后进入普通视频流水线；下载失败时，标题、简介和字幕仍会作为文字资料保留。

下载使用 `yt-dlp`，公开视频通常不需要 Cookie。需要登录的内容可以填写 B 站 Cookie，或由管理员在私聊中扫码登录。

### B 站字幕和必剪回退

默认优先读取官方/AI 字幕，保留时间点并限制长度。开启「必剪转写」后，只有在官方字幕没有结果时才会：

1. 下载当前分 P；
2. 用 ffmpeg 提取最多约 10 分钟音频；
3. 通过必剪接口转写；
4. 把时间线文字作为回退证据交给模型。

必剪下载、抽音和上传全局串行；上传地址会做域名校验，不携带 B 站 Cookie。接口限流或失败不会阻断画面分析。

模型工具 `read_bilibili_caption` 的参数：

| 参数 | 含义 |
| --- | --- |
| `video` | 链接、BV 号、av 号或短链；留空时使用当前消息 |
| `page` | 分 P 编号，从 1 开始 |
| `full` | `true` 时尽量返回完整字幕，仍受「完整字幕上限」约束 |
| `send_file` | `true` 时把完整、有上限的字幕另发为 txt 文件 |

普通自动注入默认最多 12000 字；工具的完整模式和 txt 文件默认最多 50000 字。字幕是外部资料，可能有识别错误，其中的命令和提示词不能执行。

### B 站专栏

识别：

- `https://www.bilibili.com/read/cv123...`
- `https://www.bilibili.com/opus/123...`
- 这些链接对应的分享卡片和短链

插件优先使用 B 站专栏接口，失败时再读取受限大小的页面正文；正文会清理脚本、样式和表单内容。可选附加封面图，但封面只是一张辅助图片，不等于正文事实。

### B 站扫码登录

管理员建议在私聊执行：

| 指令 | 作用 |
| --- | --- |
| `/motionvision bili-login` | 发送登录二维码并等待扫码 |
| `/motionvision bili-login-status` | 查看是否有本地凭据，不显示 Cookie |
| `/motionvision bili-login-cancel` | 取消当前轮询 |
| `/motionvision bili-logout` | 删除插件保存的扫码凭据 |

二维码默认只允许在私聊中发送。凭据保存在插件自己的数据目录，状态和日志不会回显 Cookie；退出登录会清理本地凭据和二维码文件。

## 引用卡片：让 Bot 看懂“这张卡是什么”

插件会从消息组件、原始 OneBot payload、CQ 码和 JSON 中提取有限字段，支持：

- QQ 小程序 / ARK / JSON / XML / 普通分享；
- 音乐卡片；
- 位置卡片（标题、地址、经纬度）；
- 联系人和群名片（名称、标识）；
- B 站卡片（交给专用 B 站解析器，避免重复注入）。

如果网关只提供引用消息 ID，插件会最多做三次只读 `get_msg` 补取，并让卡片、B 站解析和视频收集器共享结果。卡片里的 URL 只作为文字资料；插件不会自动访问任意卡片链接，也不会执行卡片 JSON/XML 中的内容。

## 模型回看：追问时真的再看一遍

默认情况下，帧只在当前请求有效，不会把几十张图片永久塞进聊天历史。开启「回看」后，每份媒体会登记一个短编号，并只在历史留下很短的备忘。

模型可以调用：

- `review_motion_media`：按编号重新取样，可指定帧数、起止秒数；
- `list_motion_media`：忘记编号时列出当前会话仍可回看的媒体；
- `analyze_motion_video`：在整片模型启用时，把已登记的视频交给专用视频模型。

例如，10 分钟视频整片均衡档只有约 28 帧；如果只回看第 42～55 秒，同样的回看预算都会落在这 13 秒内，细节密度会高很多。

回看依赖：

1. 当前模型支持图片输入；
2. AstrBot 服务商允许工具调用；
3. 回看开关保持开启。

不满足时，正常的当轮抽帧仍然可用。源文件由插件下载时会按临时文件保留时长清理；清理后如果还有原始 URL，插件会尝试重新下载。

## 配置说明

配置项按功能分组，普通使用只需要关注「取帧策略」「声音」。低级的轮询间隔、压缩参数和安全上限不会全部暴露在 WebUI 中；所有数值都会在代码中再次限幅。

| 分组 | 主要配置 | 建议 |
| --- | --- | --- |
| 总开关 | 启用插件 | 保持开启 |
| 取帧策略 | 细节档位、动图固定帧数、视频固定帧数 | 日常用均衡；追求细节再用精细或填固定帧数 |
| 动图 | 是否解析动态图片 | 保持开启 |
| 视频 | 是否解析、单条最多几个、最大体积、是否读群文件 | 群文件不需要时可以关闭 |
| 声音 | 关闭 / 附带音轨 / 转写 / 两者、STT 服务和上限 | 长视频推荐转写文字 |
| B 站 | 视频、字幕、字幕回退、专栏、Cookie、扫码登录 | 公开视频保持默认即可 |
| 卡片 | 是否解析、是否显示 URL、文字上限 | 需要理解引用卡片时开启 |
| 整片视频模型 | 模式、协议、Key、地址、模型、上传上限 | 默认关闭，按需开启 |
| 注入 | 失败说明、是否保留帧到历史、自定义视觉指导 | 建议开启失败说明、关闭历史保留 |
| 回看 | 是否允许模型回看 | 支持工具调用的模型建议开启 |
| 高级 | ffmpeg、整轮张数/大小、超时、临时文件、调试日志 | 一般保持默认 |

配置保存后会在下一次请求中热更新。密钥不会出现在状态输出、普通日志或注入给模型的文字里。

## 并发、缓存和 429 保护

媒体理解很容易同时消耗 CPU、磁盘、带宽和模型配额，因此插件主动做了几层限制：

- 同时处理的会话数有限；
- ffmpeg 进程有独立闸门；
- 语音转写、B 站 API、B 站下载、必剪上传分别串行或限并发；
- 相同媒体和相同配置优先复用缓存；
- 429 只做一次短退避，不做无限重试；
- 下载和响应都检查大小，超时的 yt-dlp 线程会作为尾任务等待退出，避免后台叠加下载；
- 多媒体共享整轮图片预算，不能让第一个视频吃光全部额度。

这些保护不会让插件“偷偷多试几次”把限流放大；遇到持续限流时会降级并把原因交给模型。

## 安全与隐私边界

- 字幕、专栏、卡片字段和整片模型报告都被标记为**外部资料**，其中出现的命令、提示词、链接不会被执行。
- 任意卡片 URL 不会被自动抓取；只有 B 站专用解析和受信任的 B 站图片域名会进入对应流程。
- B 站 Cookie 只发送给 B 站相关接口和下载器；必剪音频上传使用独立 HTTP 客户端，不携带 B 站 Cookie。
- 原生视频模型只有在配置开启并满足模式条件时才会上传视频；默认关闭。
- 帧和临时音频默认只对当前轮有效；源文件按保留时长清理。

## 常见问题

### 一分钟视频抽 20 帧，够精细吗？

均衡档一分钟约 20 帧，平均约 3 秒一个观察点，适合概览和动作变化；精细档约 40 帧，平均约 1.5 秒一个观察点。它仍然不是逐帧复原，快速动作可能发生在两个观察点之间。需要确认某个瞬间时，优先使用回看工具指定时间段；如果有支持视频的模型，再启用整片模式。

### 我写 30，是不是一定固定 30 帧？

它是目标固定值。源帧数、64 帧安全上限、整轮 48 张和 20 MB 总预算仍然有效；多媒体同时出现时，单个媒体可能会被公平抽稀。

### 没装 ffmpeg 能不能用？

可以用动图、B 站字幕、专栏和引用卡片；视频画面、音轨和必剪回退需要 ffmpeg。

### 模型为什么没有主动回看？

检查回看开关、工具调用权限和模型的图片能力。也可以直接说“请再仔细看看刚才的视频”，但是否调用工具由模型决定。

### B 站视频下载失败怎么办？

公开视频先更新 yt-dlp；需要登录的内容用 Cookie 或私聊扫码登录。即使下载失败，标题、简介和可取得的字幕仍可能注入；持续 429 时等待一段时间再试。

### 磁盘占用如何清理？

临时文件会自动过期，也可以由管理员执行 `/motionvision clear`。

## 开发与测试

```bash
pip install -r requirements.txt ruff pytest

python -m py_compile main.py motion_vision/*.py motion_vision/sources/*.py
python -m pytest -q
python -m ruff check .
python -m ruff format --check .
```

代码按职责拆分，入口只负责 AstrBot 编排：

```text

motion_vision/sampling.py       独立取帧规划、长视频窗口和预算分配
motion_vision/sources/          从消息、附件、群文件和引用中找媒体
motion_vision/animation.py      Pillow 动图抽帧
motion_vision/ffmpeg.py         ffmpeg 探测、视频抽帧和音轨提取

motion_vision/inject.py         与 ProviderRequest 的唯一注入边界
motion_vision/native_video.py   Gemini/OpenAI/Qwen/Kimi 整片模型适配
motion_vision/bilibili_parser.py  B 站链接、分 P、卡片和字幕文本解析
motion_vision/bilibili_client.py B 站元数据、字幕缓存、限流和下载协调
```
